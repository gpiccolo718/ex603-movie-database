# Task 1.4 — Modelling Justification & Reflection

## Modelling Justification

### Primary Keys

For the Users relation, I chose `account_id` as the primary key. Other attributes, such as `username` and `email`, must be unique per account but can be changed later, making them poor candidates for a key that should remain stable over the life of the record. `joined_date` is not unique to a single account, so it cannot serve as a key at all. `account_id` is a surrogate key: a new value is generated automatically whenever an account is created, giving every row a stable, permanent identifier independent of any user-editable data. The same reasoning applies to Movies, where I used a surrogate key, `title_id`, rather than `title` itself. Two movies can legitimately share the same title (for example, two different films both called "Frozen"), so `title` cannot guarantee uniqueness. For Ratings, the primary key is composite: `title_id` and `account_id` together. This reflects a specific business rule: a user may have only one active rating per movie at a time. If they rewatch a movie and change their opinion, that is handled as an UPDATE to the existing row rather than an INSERT of a new one, so the pair `(title_id, account_id)` is guaranteed to be unique and can safely serve as the key. Movie_Genre also uses a composite primary key, `title_id` and `genre_id`, following the standard pattern for a junction table resolving a many-to-many relationship. No single attribute uniquely identifies a row, but the pair of foreign keys does. Finally, for Genre, I used a surrogate key, `genre_id`, rather than `genre_type`. This keeps the key stable even if a genre's display name is ever edited or renamed, and is consistent with the surrogate-key approach used for Users and Movies.

### ON DELETE Behaviors

Three of the four foreign keys use CASCADE, and each case shares a common justification: the dependent row has no meaning once its parent is gone. If a user deletes their account, all their ratings are deleted with it (`Ratings.Account_ID` → `Users.Account_ID`, CASCADE). I chose this so that `average_score` on Movies always reflects only the ratings of currently active users, rather than being inflated by scores from accounts that no longer exist. Similarly, if a Movies row is deleted, its ratings are deleted with it (`Ratings.Title_ID` → `Movies.Title_ID`, CASCADE). It's important to distinguish this from a movie being taken off the platform: Movies has an `is_active` flag specifically for that case, so that a movie can be delisted and later relisted without losing its rating history. A hard DELETE from the Movies table is reserved for a different, rarer situation, such as correcting a duplicate or erroneous entry. In that case, the associated ratings are equally invalid and should be removed along with the row. The same logic extends to Movie_Genre: if a movie is deleted, its rows in the Movie_Genre junction table are deleted too (`Movie_Genre.Title_ID` → `Movies.Title_ID`, CASCADE), since a genre tag has no independent meaning once the movie it describes no longer exists. Genre is the one exception, using RESTRICT instead (`Movie_Genre.Genre_ID` → `Genre.Genre_ID`). Deleting a genre is a much rarer and more disruptive action than deleting a single movie. It would affect every movie tagged with that genre platform-wide, rather than one isolated row. RESTRICT forces an explicit cleanup step before such a structural change can occur, guarding against a genre being removed (and silently untagging potentially hundreds of movies) by accident.

### Rules Enforced in the Schema vs. Left to the Application

Several constraints are enforced directly in the schema rather than trusted to application-level validation, because the database should be the last line of defense against bad data regardless of which application, script, or future developer writes to it. The `Score` attribute on Ratings is restricted with a CHECK constraint enumerating the exact set of valid half-point values (0.5 through 5.0). Without this, an application bug or a direct database write could insert an invalid score like 3.7, silently corrupting every average calculated from it. Likewise, `NOT NULL` and `UNIQUE` constraints on `Users.email` and `Users.username` are enforced at the schema level, so that duplicate or missing values are rejected outright rather than relying on the application to check before every insert. The `average_score` attribute on Movies represents a different kind of decision. It is a derived value: the average of all `Score` entries in Ratings for a given movie. This could, in principle, always be computed live with a query rather than stored at all. I chose to store it as a denormalized, precomputed column instead, on the assumption that movie scores are read far more often than ratings are written (users browsing and comparing movies vastly outnumber the moments any single user submits or updates a rating). Storing the value trades a small amount of write-time cost for a much faster, simpler read. The cost of this decision is that the schema alone cannot guarantee `average_score` stays correct. It must be kept in sync with a trigger that recalculates it whenever a row in Ratings is inserted, updated, or deleted (including via the CASCADE deletes discussed above). This is a rule I am enforcing procedurally rather than declaratively, and it's a trade-off I made deliberately for performance rather than an oversight.

## Reflection

One decision a different designer could reasonably have made differently is the ON DELETE behavior for `Movie_Genre.Genre_ID` → `Genre.Genre_ID`. I chose RESTRICT, while the other three foreign keys in my design all use CASCADE. A different designer might argue for CASCADE here too, for consistency: every other junction or dependent row in my schema is deleted automatically once its parent is gone, and treating Genre differently introduces an exception that has to be remembered and specially handled in application logic. I chose RESTRICT specifically because of the difference in how often, and how disruptively, each type of delete would occur. Deleting a single movie or a single rating is a narrow operation, since it affects one row and, at most, a small number of dependent rows tied to that one entity. Deleting a genre is different: it is a rare, platform-wide structural change that would silently untag every movie currently associated with it, potentially hundreds of rows, in a single operation. Given how infrequently genre deletion should ever happen, and how much damage a mistaken one could cause, I was willing to accept the minor inconvenience of requiring an explicit manual cleanup step in exchange for protection against an accidental, high-impact write. For the far more frequent, low-risk deletes elsewhere in the schema, that same friction would only hurt usability without a comparable safety benefit.
